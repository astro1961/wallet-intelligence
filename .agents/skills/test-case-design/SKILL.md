# Test case design

## Источник
- Читай требования из `vault/01-Requirements/`, этапы из `vault/02-Plan/`.
- Не выдумывай требования; если их нет — заведи по шаблону и пометь `_TODO_`.

## Техники тест-дизайна
1. **Эквивалентные классы** — разбей ввод на валидные/невалидные группы, по одному представителю.
2. **Граничные значения** — 0, min, max, max+1, пустая строка, None, очень длинное значение.
3. **Таблица решений** — комбинации условий → ожидаемое действие.
4. **Попарное (pairwise)** — покрытие пар параметров, когда комбинаций много.
5. **Переходы состояний** — экраны, статусы багов/фиксов, resume/pause.
6. **Сценарии** — happy path, негатив, крайний случай, прерывание/повтор.

## Формат
Копируй `vault/_templates/TestCase.md` → `vault/07-Tests/TC-NNN.md`.
Обязательно: `requirement: "[[REQ-NNN]]"`, шаги с конкретными данными, проверяемое ожидание.

## Приоритеты
- **P1 / smoke** — приложение стартует, базовый путь работает.
- **P2 / core** — ключевые функции (добавление, отображение, обновление).
- **P3 / edge** — границы, пустые состояния, ошибки сети, редкие комбинации.

## Трассировка
`REQ-NNN → TC-NNN → RUN-...`. Каждый TC ссылается на требование; каждый RUN — на TC.
Покрытие = сколько REQ имеют хотя бы один P1/P2 TC.

## Правила
- Один TC — одна проверяемая цель (не «проверить всё»).
- Шаги воспроизводимы с конкретными данными (адрес, сумма, имя), не «какой-то кошелёк».
- Ожидание — то, что реально проверяет assert.
- Каждый найденный баг → минимум один падающий TC (регрессия).
- Перед автоматизацией — прогони TC вручную/через MCP, затем закрепи тестом.
