# Wallet Intelligence Tracker

## Техническое задание и план разработки

**Версия документа:** 1.0\
**Статус:** Спецификация MVP\
**Язык реализации:** Python 3.12+\
**Интерфейс:** TUI (Terminal User Interface)\
**Основная платформа:** Linux; архитектурная совместимость с macOS и
Windows\
**Хранение:** SQLite\
**Назначение:** локальное read-only приложение для управления массивом
криптовалютных кошельков и анализа их публичной ончейн-активности.

------------------------------------------------------------------------

## 1. Цель проекта

Разработать Wallet Intelligence Tracker --- локальную консольную утилиту
для управления большим количеством публичных криптовалютных адресов, их
группировки, мониторинга активности, анализа балансов и DeFi-позиций,
учёта проектов и тестнетов, а также визуализации связей между
кошельками, проектами, сетями и протоколами.

Приложение должно предоставлять единое рабочее пространство, в котором
пользователь может:

-   хранить и структурировать массив кошельков;
-   объединять кошельки в группы с неограниченной вложенностью;
-   импортировать адреса пакетами;
-   хранить дополнительные сведения, теги, заметки и социальные ссылки;
-   получать публичные данные из бесплатных API и пользовательских RPC;
-   отслеживать транзакции и ончейн-активности;
-   вести каталог проектов, тестнетов и пользовательских задач;
-   определять подтверждённые DeFi-позиции;
-   видеть, какие кошельки участвовали в конкретном проекте;
-   исследовать связи между кошельками и проектами;
-   работать с основными, тестовыми и пользовательскими сетями.

## 2. Границы проекта и безопасность

### 2.1. Режим работы

Приложение работает в режиме **read-only** по отношению к блокчейнам.

Запрещено реализовывать:

-   хранение seed-фраз;
-   хранение приватных ключей;
-   подписание транзакций;
-   отправку транзакций;
-   автоматическое управление активами;
-   функции, требующие доступа к средствам пользователя.

Для работы используются только публичные адреса, публичные данные
блокчейна, API-ключи поставщиков данных и пользовательские RPC.

### 2.2. Приватность

-   Хранить базу локально.
-   Не отправлять пользовательские заметки, группы и социальные ссылки
    внешним поставщикам.
-   Не передавать API-ключи в логи.
-   Не включать секреты в исходный код и репозиторий.
-   Предоставить `.env.example`, а реальные секреты хранить в локальном
    `.env`.
-   Предусмотреть резервное копирование и восстановление базы.

### 2.3. Ограничения достоверности

Приложение должно различать: 1. подтверждённые данные, полученные
непосредственно из блокчейна или надёжного индексатора; 2. данные,
полученные от стороннего API; 3. пользовательские записи; 4.
предположения, выведенные из истории транзакций.

Предполагаемые связи и позиции нельзя отображать как подтверждённые
факты. Перевод между двумя адресами сам по себе не доказывает, что они
принадлежат одному владельцу. Отсутствие найденной транзакции не
доказывает отсутствие участия в проекте.

## 3. Основные функциональные модули

### 3.1. Dashboard --- главная панель

Показывать сводную информацию по всей базе:

-   общее количество кошельков;
-   количество активных и неактивных кошельков;
-   суммарный подтверждённый баланс;
-   стоимость портфеля, если доступны цены;
-   объём подтверждённых DeFi-позиций;
-   количество проектов и тестнетов;
-   количество обнаруженных активностей;
-   состояние синхронизации и время последнего обновления;
-   последние события.

Все показатели должны поддерживать фильтрацию по группе, сети, проекту и
временному диапазону.

### 3.2. Wallet Manager --- управление кошельками

Для каждого кошелька хранить:

-   внутренний ID;
-   публичный адрес;
-   название;
-   тип адреса/блокчейна;
-   сеть или список сетей, в которых адрес отслеживается;
-   группу;
-   пользовательские теги;
-   заметки;
-   социальные ссылки;
-   дату добавления;
-   дату первой обнаруженной активности;
-   дату последней активности;
-   время последней синхронизации;
-   статус мониторинга.

Функции:

-   создание, редактирование и архивирование записи;
-   просмотр балансов и истории транзакций;
-   поиск по адресу, названию и тегам;
-   фильтрация по сети, группе, активности и балансу;
-   назначение нескольких тегов;
-   добавление социальных ссылок;
-   добавление заметок;
-   просмотр связанных проектов и кошельков;
-   история изменений метаданных кошелька.

Один публичный адрес может отслеживаться в нескольких сетях. Модель
данных не должна предполагать, что адрес уникален глобально без учёта
сети и типа блокчейна.

### 3.3. Wallet Groups --- древовидная группировка

Реализовать иерархию групп с неограниченной вложенностью.

Пример:

``` text
ALL WALLETS
├── EXCHANGES
│   ├── Binance
│   │   ├── Main
│   │   └── Subaccount 01
│   └── OKX
├── FARM WALLETS
│   ├── Farm #1
│   │   ├── Wallet 001
│   │   ├── Wallet 002
│   │   └── Wallet 003
│   └── Farm #2
├── COLD STORAGE
│   ├── Main Cold
│   └── Reserve
└── OTHER
```

Функции:

-   создание и удаление групп;
-   изменение названия и описания;
-   перемещение групп;
-   перемещение кошельков между группами;
-   вложенные группы;
-   просмотр всех кошельков внутри группы и её дочерних групп;
-   фильтрация и сортировка содержимого группы.

Удаление группы не должно автоматически удалять кошельки. Перед
удалением необходимо предложить переместить их в родительскую группу или
в `Unassigned`.

### 3.4. Bulk Import --- пакетный импорт

Поддержать:

-   вставку списка адресов в интерфейс;
-   TXT;
-   CSV;
-   JSON.

Пример CSV:

``` csv
address,name,group,network,tags
0x123...,Wallet001,Farm #1,ethereum,farming
0x456...,Wallet002,Farm #1,ethereum,active
0x789...,Cold01,Cold Storage,ethereum,cold
```

Процесс импорта:

1.  Загрузка или вставка данных.
2.  Определение формата.
3.  Валидация адресов и полей.
4.  Проверка дубликатов.
5.  Проверка соответствия сети и типа адреса.
6.  Предварительный просмотр результатов.
7.  Выбор группы для записей без группы.
8.  Подтверждение импорта.
9.  Сохранение новых записей.
10. Отчёт об успешных, пропущенных и ошибочных строках.

Режим по умолчанию --- добавлять только новые записи. Обновление
существующих записей допускается только после отдельного подтверждения
пользователя.

Импорт больших файлов должен выполняться без блокировки TUI.

### 3.5. Activity Tracker --- отслеживание активностей

Категории событий:

-   Testnet interaction;
-   Airdrop-related activity;
-   Swap;
-   Bridge;
-   DeFi interaction;
-   NFT;
-   Token transfer;
-   Staking;
-   Contract interaction;
-   Custom activity.

Поля события:

-   ID;
-   кошелёк;
-   сеть;
-   проект, если определён;
-   transaction hash, если применимо;
-   тип события;
-   дата и время;
-   адрес контракта;
-   токен;
-   количество;
-   статус;
-   источник данных;
-   ссылка на обозреватель;
-   признак автоматического или ручного создания;
-   дополнительные метаданные.

Функции:

-   фильтрация по кошельку, проекту, сети, типу и дате;
-   сортировка;
-   поиск;
-   просмотр деталей транзакции;
-   автоматическая подсветка кошельков, взаимодействовавших с выбранным
    проектом;
-   ручное добавление активности;
-   отметка пользовательской задачи как выполненной;
-   экспорт результатов.

Автоматически обнаруженные ончейн-события и ручные отметки задач должны
храниться раздельно.

### 3.6. Project Manager --- проекты и тестнеты

Создать каталог проектов.

Поля проекта:

-   ID;
-   название;
-   описание;
-   категория;
-   статус;
-   поддерживаемые сети;
-   известные адреса контрактов;
-   официальные ссылки;
-   заметки;
-   дата создания и обновления.

Категории могут включать:

-   Testnet;
-   Mainnet ecosystem;
-   DeFi;
-   Airdrop campaign;
-   NFT;
-   Other.

Статусы:

-   Active;
-   Paused;
-   Completed;
-   Archived.

Функции:

-   создание и редактирование проекта;
-   привязка нескольких сетей;
-   добавление контрактов;
-   ручная привязка кошельков;
-   автоматическая привязка при обнаружении взаимодействия с известным
    контрактом;
-   список всех задействованных кошельков;
-   история активностей проекта;
-   статистика по числу кошельков и взаимодействий;
-   пользовательские задачи и чек-листы по каждому кошельку.

Пример представления:

``` text
PROJECT: MONAD TESTNET
Networks: Monad Testnet
Participating wallets: 18
Detected interactions: 142

Farm #1
├── Wallet 001 — 12 interactions
├── Wallet 002 — 8 interactions
└── Wallet 003 — 5 interactions

Farm #2
├── Wallet 014 — 4 interactions
└── Wallet 015 — 7 interactions
```

Статус участия должен иметь источник: `detected`, `manual` или `task`.
Не считать автоматическое обнаружение полным реестром участия.

### 3.7. DeFi Analyzer --- отслеживание DeFi-позиций

Функции:

-   получение токен-балансов;
-   получение доступных цен;
-   расчёт оценочной стоимости;
-   определение известных протоколов;
-   отображение подтверждённых DeFi-позиций;
-   распределение активов по протоколам и сетям;
-   история стоимости;
-   фильтрация по кошельку, группе, сети и протоколу.

Разделять результаты на:

1.  Wallet balances --- активы непосредственно на адресе.
2.  Confirmed DeFi positions --- позиции, подтверждённые данными
    протокола или индексатора.
3.  Inferred positions --- предположения на основании истории
    взаимодействий.

Транзакция с контрактом протокола не является доказательством наличия
текущей позиции. Если поставщик не предоставляет данные о позиции,
отображать её как неизвестную или предполагаемую, а не включать в
подтверждённую сумму.

Поля сети:

-   decimals;

-   приоритет RPC;

Функции:

-   добавление и редактирование сети;

-   проверка соединения;
-   проверка Chain ID;
-   несколько RPC для сети;
-   переключение основного RPC;
-   резервный RPC;
-   отображение статуса подключения.

Не считать произвольный RPC безопасным или доверенным только потому, что
он отвечает на запросы. Не отправлять ему приватные данные.

## 4. Источники данных и интеграции

### 4.1. Общий подход

Создать независимый слой `Data Providers`. Бизнес-логика не должна
зависеть от конкретного поставщика.

Предусмотреть адаптеры:

-   Etherscan API;
-   Blockscout API;
-   DeFiLlama API;
-   EVM JSON-RPC;
-   Solana JSON-RPC (отдельный этап);
-   Custom RPC.

Официальная документация:

-   Etherscan: https://docs.etherscan.io/
-   Blockscout: https://docs.blockscout.com/
-   DeFiLlama: https://api-docs.defillama.com/
-   Solana RPC: https://solana.com/docs/rpc

Перед реализацией проверить актуальные условия бесплатных тарифов,
лимиты, доступность сетей и требования к API-ключам. Не предполагать,
что все эндпоинты бесплатны или неограниченны.

### 4.2. Требования к адаптерам

Каждый адаптер должен реализовывать согласованный интерфейс, например:

-   `get_native_balance(address, network)`;
-   `get_token_balances(address, network)`;
-   `get_transactions(address, network, cursor)`;
-   `get_transaction_details(tx_hash, network)`;
-   `get_token_metadata(contract, network)`;
-   `get_latest_block(network)`;
-   `health_check(network)`.

Методы, которые не поддерживаются конкретным провайдером, должны
возвращать явно обозначенный статус `unsupported`, а не фиктивные
данные.

### 4.3. Надёжность API

Реализовать:

-   тайм-ауты;
-   повторные запросы с exponential backoff;
-   rate limiting;
-   пагинацию;
-   кэширование;
-   health checks;
-   обработку HTTP и RPC ошибок;
-   логирование без секретов;
-   контроль квот и лимитов;
-   переключение между провайдерами.

При недоступности API показывать последние сохранённые данные и время их
обновления.

### 4.4. Конфигурация

Использовать `.env` для секретов и `config.yaml` для обычных настроек.

Пример `config.yaml`:

``` yaml
app:
  name: Wallet Intelligence Tracker
  refresh_interval_seconds: 300
  timezone: UTC

database:
  path: data/wallet_tracker.db

providers:
  etherscan:
    enabled: true
    api_key_env: ETHERSCAN_API_KEY

  blockscout:
    enabled: true
    api_key_env: BLOCKSCOUT_API_KEY

  defillama:
    enabled: true

networks:
  - name: Ethereum
    type: evm
    chain_id: 1
    enabled: true

  - name: Arbitrum
    type: evm
    chain_id: 42161
    enabled: true

  - name: Base
    type: evm
    chain_id: 8453
    enabled: true
```

Не хранить реальные API-ключи в `config.yaml`, если файл может попасть в
репозиторий.

## 5. Synchronization Engine

Создать независимый асинхронный механизм синхронизации.

Функции:

-   первичная синхронизация кошелька;
-   инкрементальное получение новых данных;
-   ручное обновление;
-   периодическое обновление;
-   ограничение параллельных запросов;
-   хранение курсоров и последнего обработанного блока;
-   защита от дублирования событий;
-   пауза и возобновление;
-   отображение прогресса;
-   обработка частичных ошибок.

Синхронизация не должна блокировать главный поток TUI.

Для каждой комбинации кошелька, сети и типа данных хранить отдельный
курсор, если это необходимо провайдеру.

Повторная обработка одного и того же события не должна создавать
дубликаты. Использовать устойчивые внешние идентификаторы, например
сеть + transaction hash + индекс события.

## 8. Модель данных

Минимальный набор сущностей:

  Сущность          Назначение

  WalletSocial      Социальные ссылки
  WalletRelation    Связи между кошельками
  Network           Блокчейн-сеть
  RpcEndpoint       RPC-адрес и его приоритет
  Project           Проект или тестнет
  ProjectContract   Контракт проекта в сети
  ProjectWallet     Участие кошелька в проекте
  ProjectTask       Пользовательская задача
  Activity          Ончейн-событие или ручная активность
  Transaction       Транзакция
  Token             Метаданные токена
  BalanceSnapshot   История балансов
  DeFiPosition      Подтверждённая или предполагаемая позиция
  Provider          Конфигурация источника данных
  SyncJob           Задача синхронизации
  SyncCursor        Позиция последней синхронизации

Требования к моделированию:

-   использовать внешние ключи и ограничения целостности;
-   создать индексы для адресов, сетей, transaction hash, проектов и

-   использовать `Decimal` или точное целочисленное представление для
    финансовых значений;
-   не использовать `float` для точных токеновых сумм;
-   хранить исходные единицы токена и decimals;
-   хранить время в UTC;
-   предусмотреть уникальные ограничения для предотвращения дублей;
-   предусмотреть миграции схемы.

## 9. TUI --- требования к интерфейсу

Использовать Textual и единый визуальный стиль.

Основные разделы:

1.  Dashboard
2.  Wallets
3.  Activities
4.  Projects
5.  DeFi
6.  Networks
7.  Graph
8.  Import
9.  Settings

### 9.1. Общая компоновка

-   верхняя строка: название приложения, состояние синхронизации, время
    последнего обновления;
-   боковая панель: навигация;
-   центральная область: содержимое выбранного раздела;
-   нижняя строка: доступные горячие клавиши и контекстные действия.

### 9.2. Горячие клавиши

  Клавиша   Действие
  --------- --------------------------
  `1–9`     Переключение разделов
  `↑ / ↓`   Навигация
  `Enter`   Открыть или подтвердить
  `/`       Глобальный поиск
  `A`       Добавить кошелёк
  `I`       Импорт
  `R`       Обновить
  `F`       Фильтры
  `G`       Открыть граф
  `Esc`     Назад или закрыть диалог
  `Q`       Выход

Горячие клавиши не должны конфликтовать с вводом текста в полях. В
текстовых полях стандартные клавиши редактирования должны работать
ожидаемо.

### 9.3. Адаптивность

-   поддержать изменение размера терминала;
-   не обрезать критически важные данные;
-   при узком окне перестраивать панели вертикально;
-   предусмотреть пустые состояния, ошибки загрузки и состояния
    отсутствия API-данных;
-   обеспечить читаемость при стандартных терминальных шрифтах.

## 10. Нефункциональные требования

### Производительность

-   длительные операции не блокируют интерфейс;
-   таблицы должны поддерживать пагинацию или виртуализацию;
-   большие импорты обрабатываются пакетами;
-   API-запросы ограничиваются семафорами и rate limiter;
-   индексы базы данных используются для частых запросов;
-   кэш не должен приводить к отображению устаревших данных без
    соответствующей отметки.

### Надёжность

-   ошибки одного провайдера не останавливают всё приложение;
-   некорректная строка импорта не отменяет весь импорт;
-   прерванная синхронизация может быть безопасно продолжена;
-   база данных должна корректно закрываться при выходе;
-   предусмотреть резервное копирование и восстановление.

### Тестирование

Использовать Pytest.

Обязательные категории:

-   unit tests для валидаторов и бизнес-логики;
-   тесты групп и вложенности;
-   тесты импорта CSV/TXT/JSON;
-   тесты дедупликации;
-   тесты репозиториев и миграций;
-   тесты адаптеров на mock-ответах;
-   integration tests для синхронизации;
-   тесты обработки ошибок и rate limits.

Тесты не должны зависеть от реальных API или доступности интернета. Для
этого использовать фикстуры и mock-серверы.

## 12. Критерии готовности MVP

MVP считается готовым, если:

1.  Приложение запускается одной командой.
2.  Создаётся и открывается SQLite-база.
3.  Пользователь может добавлять, редактировать и архивировать кошельки.
4.  Работает древовидная группировка.
5.  Работают теги, заметки и социальные ссылки.
6.  Работает пакетный импорт CSV, TXT и JSON.
7.  Есть проверка адресов и дубликатов.
8.  Подключён минимум один реальный источник данных для EVM.
9.  Получаются native balance и история транзакций поддерживаемой сети.
10. Данные сохраняются локально.
11. Синхронизация инкрементальная.
12. Интерфейс не блокируется во время запросов.
13. Ошибки API отображаются без аварийного завершения приложения.
14. Реализованы проекты и привязка кошельков.
15. Основная бизнес-логика покрыта тестами.
16. Есть README с инструкциями по установке и запуску.

Функции DeFi-позиций, Solana и расширенного графа могут оставаться за
пределами первого MVP, но архитектура должна предусматривать их
добавление.

## 13. Инструкции AI-разработчику (Antigravity)

Ты должен работать как автономный инженерный агент, но соблюдать
поэтапную разработку.

### Общие правила

-   Не реализовывай весь проект одним большим файлом.
-   Не создавай фиктивные данные в production-режиме.
-   DEMO-данные должны быть явно обозначены.
-   Не подменяй реальные API-ответы статическими значениями.
-   Не размещай секреты в исходном коде.
-   Не добавляй зависимости без необходимости.
-   Не переписывай работающие модули без обоснования.
-   Не смешивай UI, бизнес-логику, провайдеры и базу данных.
-   Не переходи к следующему этапу, пока текущий не проходит тесты.

### Рабочий цикл каждого этапа

1.  Изучи текущую структуру проекта.
2.  Сформулируй краткий план изменений.
3.  Реализуй функциональность.
4.  Запусти тесты.
5.  Исправь найденные ошибки.
6.  Проверь совместимость с предыдущими этапами.
7.  Обнови README и техническую документацию.
8.  Подготовь отчёт: что сделано, какие тесты пройдены, какие
    ограничения остались.

Если обнаружена неоднозначность, влияющая на архитектуру или данные,
сначала опиши варианты и выбери наиболее безопасный и расширяемый
вариант. Не блокируй работу вопросами по несущественным деталям.

### Первое задание

Начни только с Этапа 1.

Сначала проверь окружение и доступные версии Python. Затем:

1.  Создай структуру проекта.
2.  Настрой `pyproject.toml`.
3.  Реализуй конфигурацию.
4.  Реализуй подключение к SQLite и базовые модели.
5.  Настрой миграции.
6.  Создай Textual-приложение.
7.  Реализуй основную навигацию и пустые экраны всех разделов.
8.  Добавь статусную строку и горячие клавиши.
9.  Добавь минимальные тесты.
10. Проверь запуск приложения.

Не начинай интеграцию внешних API и не переходи к Этапу 2 до завершения
Этапа 1.

В конце выведи отчёт с командами установки и запуска, структурой
созданных файлов, результатами тестов и перечнем оставшихся задач.
